# 主流 VPS 测评程序对标分析

本文档用于沉淀 Perfassess 对主流 VPS 测评工具的分析结论，明确哪些能力应该吸收、哪些历史包袱不应复刻，以及后续企业级演进顺序。

## 对标对象

本次分析优先参考仓库内 `study/` 目录中的三个本地样本：

- `study/yet-another-bench-script`: 代表 YABS 类性能测评口径。
- `study/IPQuality`: 代表 IP 质量、风险、邮局、流媒体和在线报告体验。
- `study/RegionRestrictionCheck`: 代表流媒体与区域限制检测覆盖。

这些样本只作为产品和口径参考，不直接复刻历史包袱代码。Perfassess 的实现原则是：保留 Go 模块化、结构化 JSON、可验证报告契约和隐私默认关闭。

### YABS / bench.sh 类性能测评

代表能力：

- 一条命令直接运行，输出适合复制分享的终端报告
- 使用业内常见后端，例如 fio、iperf3、Geekbench
- 磁盘报告按混合随机读写矩阵展示，便于横向对比
- 网络报告按多地区节点展示上下行吞吐和延迟
- 明确提供跳过测试、减少网络节点、JSON 输出等参数

值得吸收：

- 主流基准后端优先，而不是只依赖项目内置轻量测试
- 报告要适合复制、截图和横向比较
- 长耗时、高流量测试必须有明确档位和提示
- JSON 输出应可被外部平台或后续系统消费

不应复刻：

- 依赖未授权公共节点或不稳定下载源作为核心结论
- 在报告中把失败节点静默隐藏
- 把外部二进制下载和执行做成默认黑盒行为

Perfassess 当前状态：

- 已接入 sysbench、fio、iperf3、speedtest 和 Geekbench 边界
- 已支持 fio mixed 矩阵、iperf3 多节点矩阵和分享模板
- 已支持 JSON/text/Web 多种输出
- iperf3、speedtest、fio 和 sysbench 已接入结构化错误分类，便于区分依赖缺失、许可或参数不兼容、权限不足、资源不足、网络不可达、超时、命令失败和解析失败
- 仍需要授权节点元数据、真实样本校准，以及用更多真实外部后端失败样本继续修正分类边界

企业级吸收方式：

- 默认路径仍使用安全、低依赖、可完成的 builtin 档位，避免低配机器直接失败。
- `mainstream` 档位明确启用 sysbench/fio 等主流后端，用 `confidence_level` 标记更高可比性。
- Geekbench 只作为显式可选后端，不默认下载运行外部闭源二进制。
- iperf3 只接受用户自有或授权节点，不内置未经确认的公共节点池。
- YABS 风格的表格输出应保留，但背后必须有 JSON schema 和报告契约测试支撑。

### IPQuality / NodeQuality 类 IP 质量检测

代表能力：

- IP 基础信息、类型、风险分、风险来源、DNSBL、邮件端口、流媒体、AI 服务集中展示
- 支持 IPv4/IPv6 双栈，支持 JSON/ANSI/纯文本输出
- 报告排版适合截图和传播
- 对风险来源和证据进行分组，不只给一个总分

值得吸收：

- IP 质量要分成基础信息、风险因子、黑名单、邮件端口、解锁能力和建议
- 结论必须能追溯到证据来源
- 报告要区分“可用”“受限”“不可用”“未执行”
- 隐私和在线报告能力应显式选择，不应默认上传

不应复刻：

- 把多个外部风险源混成不可解释的黑盒分数
- 把启发式网页检测当成强结论
- 默认生成或上传在线报告

Perfassess 当前状态：

- 已有 IP 质量模块、风险来源、证据可信度摘要、DNSBL、邮件端口、网络栈、流媒体和 AI 服务摘要
- 已在控制台、Markdown、Web 和模块 JSON 中展示 IP 质量
- 仍需要更多风险源可配置化、检测超时预算和真实样本回归

企业级吸收方式：

- IP 质量不只给“好/坏”，而是拆成基础属性、风险来源、黑名单、邮件连通、网络栈、解锁能力和建议。
- 每个外部来源都应记录状态：`success`、`skipped`、`timeout`、`failed`、`unsupported`。
- 风险分只作为汇总视图，不能覆盖原始证据和来源说明。
- 在线报告、上传和完整 IP 展示必须显式选择，默认不上传、不公开精确身份信息。
- 控制台报告应保留一屏截图友好格式，Web 报告负责承载完整证据表。

### RegionRestrictionCheck 类流媒体解锁检测

代表能力：

- 低依赖、可在多类 Unix 环境运行
- 平台按地区或类别组织
- 支持 IPv4/IPv6、网卡、语言等运行参数
- 对不同平台返回“完整解锁、部分解锁、受限、不可用”等细分结果

值得吸收：

- 流媒体平台必须分组展示，不能只堆平铺列表
- 结果应包含区域、解锁类型、判断依据和提示信息
- quick/standard/full 档位要控制耗时和请求数量
- 检测失败应显示原因，而不是只显示不可用

不应复刻：

- 大量 shell 分支逻辑带来的维护负担
- 没有 schema 契约的输出格式
- 过度依赖平台页面细节导致频繁失效

Perfassess 当前状态：

- 已支持流媒体 quick/standard/full 档位、分组报告和单平台证据可信度摘要
- 已在 Web/控制台/Markdown 中展示解锁类型和区域提示
- 仍需要更严格的平台检测超时、失败归因和回归样本

企业级吸收方式：

- 平台检测以 quick/standard/full 分层，不把全量平台作为默认路径。
- 结果必须区分“完整解锁、部分解锁、仅自制、受限、不可用、未执行、检测失败”。
- 每个平台保留判断依据，例如 HTTP 状态、跳转地区、API 区域、DNS 结果或错误类型。
- 对易失效平台增加回归样本和超时预算，避免单个平台拖垮整轮测评。
- AI 服务检测和流媒体检测共用“可达性 + 区域 + 证据 + 限制”的报告语义。

## 对标差距矩阵

| 能力域 | 主流工具成熟做法 | Perfassess 已有能力 | 下一步差距 |
| --- | --- | --- | --- |
| 一键运行 | `curl | bash`、自动准备临时环境、完成后提示报告 | `bootstrap.sh` 可安装基础依赖、构建、测评、Web 进度 | 需要继续验证低内存、重复运行、失败摘要和清理路径 |
| 性能口径 | fio mixed、iperf3 多节点、Geekbench/sysbench | 已有 fio mixed、iperf3 矩阵、授权节点文件、sysbench/Geekbench 边界和外部后端结构化错误分类 | 需要真实授权节点样本、真实失败样本回归和评分样本校准 |
| IP 质量 | 多源风险、DNSBL、邮件、流媒体、AI 集中展示 | 已有 IP 质量、风险来源、证据可信度、邮件端口、网络栈摘要 | 需要更多来源可配置化、超时预算和真实样本回归 |
| 流媒体 | 按地区/平台分组，IPv4/IPv6 可选 | 已有 quick/standard/full 和分组输出 | 需要更多失败归因、平台回归样本和 Web 证据表 |

| 发布质量 | 社区脚本多靠实机口碑 | 已有 validate、release-check、vps-acceptance | 需要真实 VPS 样本集和正式发布验收记录 |

## 企业级完成标准

Perfassess 进入企业级可发布状态，不能只看功能数量，应同时满足以下条件：

- **运行可靠**：全新服务器可以一条命令完成准备、构建、测评、报告、清理；512MB 低配机器也能给出可解释结果。
- **结果可信**：所有估算、跳过、降级、失败都有结构化原因；报告不会把低置信结果包装成强结论。
- **口径可比**：mainstream 档位能稳定使用 sysbench/fio/speedtest 或授权 iperf3，结果可和主流脚本横向讨论。
- **报告一致**：控制台、Markdown、JSON、Web 共享同一套结论、证据、限制和建议语义。
- **产物可验**：报告目录和 zip 包有 manifest、SHA256、篡改校验和 schema 契约。
- **发布可控**：CI、release workflow、本地 release-check、真实 VPS acceptance 形成闭环。
- **隐私默认安全**：默认不上传，不保留长期历史，不公开完整敏感信息；上传和样本收集都必须显式选择。

## 下一批实现顺序

### 1. 发布基线收口

当前工作区已经包含大批报告、自动化和验收改动。下一步应先完成验证并拆分提交，形成一个可回滚、可测试、可发布的基线。

验收门槛：

- `git diff --check`
- `bash -n install.sh uninstall.sh scripts/*.sh`
- `python3 -m py_compile scripts/perfassess-progress-server.py scripts/calibration-summary.py scripts/verify-artifacts.py`
- `make validate`
- 发布前额外执行 `make release-check`

### 2. 真实 VPS 样本闭环

在真实机器上优先跑：

```bash
PERFASSESS_ACCEPTANCE_MATRIX=low,standard scripts/vps-acceptance.sh
```

样本收集要求：

- 每台机器保存 `/tmp/perfassess-auto/calibration_sample.json`。
- 先达到 candidate 数据集，再考虑 formal 数据集。
- 低配、普通、较高配置机器要分层收集，避免评分只适合单一机器类型。

### 3. 报告产品化

Web 和控制台报告继续按“结论优先”推进：

- 首屏显示是否适合当前用途、总分、置信度、核心短板和优先建议。
- 模块页显示关键指标、证据、限制、建议、原始产物入口。
- IP、流媒体、AI、路由都必须明确“检测依据”和“不能证明什么”。

### 4. 主流后端稳定化

优先增强：

- `iperf3` 节点文件校验、授权声明、节点元数据、失败节点不静默隐藏。
- `speedtest` 节点、出口 IP、jitter、结果 URL 的报告一致性。
- `fio` direct I/O、磁盘空间、权限、文件系统限制的错误分类。
- `sysbench` 在低内存和低 CPU 机器上的时间预算和跳过解释。

### 5. 平台化边界

暂不恢复默认本地历史库，不内置真实回程探针，不默认上传在线报告。后续如果要做平台化，应先做：

- 显式上传到用户自有 endpoint。
- 脱敏报告导出和导入。
- 外部系统按 schema 做排行、对比和长期趋势。
- 授权节点池的安全设计与滥用防护。

## Perfassess 的产品定位

Perfassess 不应只是“另一个脚本集合”。它的差异化应是：

- 默认一把梭可运行，低配机器不会直接崩掉
- 主流后端可选，结果可解释，估算路径明确标记
- JSON schema 稳定，适合自动化系统消费
- 控制台、Markdown、Web 报告共享同一套结果语义
- 失败或跳过测试时保留部分结果，不生成空报告
- 不默认上传报告、不默认长期追踪本地历史，保护用户隐私

## 已吸收能力

- bootstrap 一键安装基础依赖、拉取源码、构建和测评
- low-memory 模式，低内存机器自动降并发、可建临时 swap、跳过单元测试
- basic/standard/full 测评档位
- builtin/mainstream 后端质量档位
- 控制台心跳和 Web 实时进度
- 失败时生成 `summary.md` 和日志尾部
- 部分测试失败时保留已完成结果，并标记失败或跳过项
- `assessment_conclusion` 测评结论，说明适用场景、短板、限制和建议
- `quality_notes`、`confidence_level`、`score_breakdown`、`score_calibration`
- 主流外部后端错误分类：iperf3、speedtest、fio 和 sysbench 会把常见失败映射为依赖缺失、许可或参数不兼容、权限不足、资源不足、网络不可达、超时、命令失败或解析失败，并写入 metrics 供报告层解释
- iperf3 节点文件要求 `auth=owned|authorized`，支持节点名称、地区、提供方元数据，并使用文档保留地址作为示例，避免误导用户直接使用未授权公共节点
- 模块化产物：硬件、网络、路由、国内方向参考、IP 质量、压缩包
- IP 质量证据可信度摘要：按身份信息、DNSBL、邮件连通、本地启发式和商业风险 API 边界展示状态、置信度、影响和限制
- 流媒体和 AI 服务证据可信度摘要：按访问响应、区域线索、账号/API 或播放验证边界展示状态、置信度、影响和限制
- 路由追踪证据可信度摘要：按路径方向、可见跳点、超时失败和真实回程边界展示状态、置信度、影响和限制
- Web 完整报告按侧边栏模块展示，并在首页提供结论优先的决策面板、关键证据、短板排序和优先建议；模块卡片展示证据、限制和建议，路由模块明确标记本机出站路径不是真实回程
- 报告产物清单记录文件大小、SHA256 和压缩包收录状态，并支持校验目录和 zip 包
- 脱敏校准样本和校准汇总工具已建立，支持 exploratory/candidate/formal 数据集准入检查、`Collection Plan`、`Score Profile Policies` 和 `--require-score-profiles` 多档位门禁
- VPS 验收摘要已展示单份报告的 `sample_policy`、整体 `calibration_readiness` 和 readiness 计数，便于判断报告是否适合进入校准样本池
- 移除默认本地历史追踪，只保留一次性目录排序

## 仍需补齐的企业级能力

### P0：结果可信度闭环

- 继续扩大 `assessment_conclusion`、模块证据和 Web 首屏契约测试覆盖，确保未完成报告不会给出强适用结论
- 将估算、跳过、降级、外部依赖缺失统一为结构化原因，并在控制台、Markdown、Web 和 JSON 中保持一致；主流外部后端已覆盖常见错误分类，下一步用真实样本校准边界
- 对真实服务器样本做评分回测，校准 `2026-06-v1` 后续版本

### P1：主流后端稳定化

- 使用真实自有或授权 iperf3 节点做矩阵样本回归，验证节点标签、失败节点保留、上下行统计和授权声明在控制台、Markdown、Web、JSON 中一致展示
- 基于真实 VPS 外部后端失败样本继续修正错误分类，避免把许可、参数版本、资源、网络和平台限制误判为机器性能问题
- 对 full 档位增加明确时间预算和资源预算
- 给外部后端补充 release smoke 中的可选验收路径

### P2：报告产品化

- Web 报告首页增加“结论优先”的模块顺序
- 报告模块增加证据表和建议表，而不是只展示指标
- Markdown 摘要保持论坛可复制风格，同时避免过长
- 控制台输出继续保持一屏总览 + 分节详情

### P3：平台化边界

- 支持显式上传到用户自有 endpoint，但默认关闭
- 支持脱敏导出报告，用于样本校准
- 支持外部系统按 schema 导入报告做排行和对比
- 如果未来恢复趋势能力，应由显式数据目录或外部平台承担，不恢复默认本地历史库

## 下一阶段建议

下一阶段优先做“发布收口和真实校准闭环”：

1. 用真实 VPS 执行 `low`、`standard` 和必要的 `full/mainstream` 验收矩阵，确认低内存、长耗时和外部依赖缺失时都能生成可解释报告。
2. 收集脱敏 `calibration_sample.json`，先达到 candidate 数据集，再评估 formal 校准集。
3. 保持控制台、Markdown、Web 和 JSON 报告共享同一套结论、证据、限制和建议语义。
4. 对授权 iperf3 节点、speedtest、fio、sysbench 的失败原因继续细分，避免把外部环境问题误判为机器性能问题。

这样 Perfassess 会从“能解释为什么这么判断”继续升级为“能在真实服务器和发布流程里持续证明自己可靠”的评估产品。
